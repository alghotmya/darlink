Phase 1 MVP — System Design, Architecture & Requirements Guide

Real estate marketplace for UAE, GCC and Egypt (rent/lease + buy/sell). Multi-tenant SaaS, REST API, no tokenization. This document describes the application concept, high-level architecture, data model, and business/functional/non-functional requirements.

1. Application Overview

DarLink is a Bayut-style real estate marketplace targeting Phase 1 MVP for UAE, GCC and Egypt. It supports:

  • Rent/lease and buy/sell listings
  • Multi-tenant SaaS — multiple organizations (brokerages, landlords, property managers) with tenant isolation
  • Public browsing — search, filter, listing details, and lead submission (contact agent CTA)
  • Org-scoped operations — listing CRUD, media upload (presigned S3), admin key–protected endpoints

Phase 1 explicitly excludes tokenization, KYC/AML, and wallets; the stack is REST-only (no AppSync/GraphQL). Compliance posture is informed by VARA-style auditability (immutable audit logs, append-only) without implementing tokenization in MVP.

2. User Personas

DarLink serves several types of users. Understanding who they are and what they need helps clarify feature scope and priorities.

Public / Anonymous

Property seeker (tenant or buyer)

Browses listings without logging in. Wants to find a property (rent or buy), view details and photos, and contact the listing owner or agent. Submits a lead (name, email, phone, message) from the listing page. May later sign up to track applications or saved listings (Phase 2).

Authenticated — Org member

Agent / Broker / Landlord / Property manager

Belongs to an organization (brokerage, landlord, or property management company). Creates and manages listings (draft → publish → pause/archive or mark leased/sold). Uploads media via presigned URLs. Views and manages leads for their org’s listings. May handle applications and offers (Phase 2).

Authenticated — Admin

Organization admin

Manages the organization: invites users, assigns roles, views audit logs. Has access to org-scoped listing CRUD and media. May moderate content or handle escalation (Phase 2).

System

API consumer (e.g. partner or mobile app)

Uses REST API with admin key or (Phase 2) JWT to manage listings and media on behalf of an org. Same capabilities as agent/broker from an API perspective.

3. High-Level Architecture

The system is built on AWS with a clear separation: React frontend (Amplify), REST API (API Gateway + Lambda), DynamoDB (single-table), S3 (media), and Cognito (auth).

GSIs

Listing status lifecycle (property dynamics)

Listings support a full lifecycle so properties can be marked as leased (rent) or sold (sale) when the deal closes. Only published listings appear in public browse; leased and sold are closed outcomes and are excluded from public search.

draft → published → leased (rent) | sold (sale)

Optional transitions: published → paused (temporarily hide) or archived (remove from marketplace). When setting status to leased or sold, set closedAt to the current ISO timestamp for reporting and audit.

5. Business Requirements

  • Multi-tenant marketplace — Support multiple organizations (brokerages, landlords, property managers) with strict tenant isolation (orgId on every record; no cross-org data access).
  • Rent/lease and buy/sell — Listings support type rent or sale with price, currency, and location attributes for UAE/GCC/Egypt.
  • Lead capture — Public users can submit leads (name, email, phone, message) from a listing page; leads are stored per org and listing for broker/agent follow-up.
  • Listing lifecycle — Listings move through draft → published → (optional) paused/archived. Only published listings appear in public browse; org-scoped CRUD and media upload for authorized callers.
  • Auditability — Critical actions (listing create/update/publish, lead submission, application/contract status changes) must be supportable by an immutable, append-only audit log queryable by org and time (Phase 2 implementation; model and GSI ready).
  • No tokenization in Phase 1 — No wallets, KYC/AML, or token flows; compliance mindset (e.g. VARA-aware) without implementing regulated features in MVP.

6. Functional Requirements

Public (no login)

Browse listings

Search/filter/sort/paginate published listings (e.g. by country, type). Map-ready fields (lat/lng) present; map integration optional.

Listing detail

View single listing with gallery (mediaKeys → presigned or public-read URLs as implemented), description, price, location, and contact CTA.

Lead submission

Submit lead form (name, email, phone, message) for a published listing; stored as Lead linked to listing and org. WhatsApp/callback placeholders acceptable.

Agent/agency pages

Public agent profile and agency pages (placeholders or stubs acceptable in MVP).

Authenticated (role-based)

Listings management

Agents/brokers/landlords/PMs: create, update, delete listings; publish/pause; attach media via presigned upload then add keys to listing.

Leads inbox

View and manage leads by org (and optionally by listing/agent); basic pipeline status (new, contacted, qualified, closed).

Applications & offers/contracts

Lightweight rental application and contract/offer placeholders with real status; full workflows in later phases.

Admin

Org and user management (invites), audit log viewer, moderation flags. Implemented to the extent of admin-protected org listing CRUD and media presign in Phase 1.

AuthN/AuthZ (Phase 1 vs Phase 2)

Phase 1: Cognito User Pool exists; public and admin-key–protected endpoints are implemented. Cognito authorizer on API Gateway and full RBAC/org-scoped auth (e.g. JWT validation in Lambdas) are targeted for Phase 2.

7. User Journeys

User journeys describe end-to-end scenarios from the user’s perspective: goal, context, and main steps. They complement functional requirements by showing how features fit together.

Journey 1: Find a property and submit an inquiry

Who: Property seeker (anonymous). Goal: Find a rental or sale listing and get in touch with the agent/owner.

  • Open DarLink (web).
  • Browse or search listings (filter by country, type rent/sale, optional city).
  • Open a listing to view details, photos, price, location.
  • Decide to inquire → fill lead form (name, email, phone, message) and submit.
  • Receive confirmation (or redirect); agent/org receives the lead in their inbox (Phase 2 UI) or via backend.

Journey 2: Publish and manage a listing

Who: Agent, broker, or landlord. Goal: Add a property, attach photos, publish it, and later mark it leased/sold or pause it.

  • Sign in (Phase 2) or use admin key / API.
  • Create a new listing (draft): title, description, price, type, location, attributes.
  • Request presigned URLs, upload photos to S3, add returned keys to the listing.
  • Publish the listing → it appears in public browse.
  • Later: update details, pause (temporarily hide), or set status to leased/sold and optionally set closedAt.

Journey 3: Manage leads and close a deal

Who: Agent or property manager. Goal: See incoming leads, follow up, and when a deal closes, mark the listing as leased or sold.

  • Access leads inbox (org-scoped; Phase 2 UI or API).
  • View leads per listing; update status (new → contacted → qualified → closed).
  • When tenant/buyer signs: mark listing as leased (rent) or sold (sale); listing disappears from public browse.

Journey 4: Admin manages organization

Who: Org admin. Goal: Invite users, assign roles, and review audit trail.

  • Create or manage organization (Phase 2).
  • Send invites (email, role); users accept and join org.
  • View audit log for the org (listing changes, lead submissions, status updates) for compliance and support.

8. User Flows

User flows are step-by-step sequences for key actions. They clarify the exact order of screens or API calls and help implement and test features.

Flow A: Public — Browse and submit lead

1
Open app

User visits the DarLink URL (Amplify or local). Home or Listings page loads.

2
List listings

Frontend calls GET /public/listings (optional query: country, type, limit, nextToken). Results displayed as cards or list.

3
Open listing detail

User clicks a listing. Frontend calls GET /public/listings/{id}. Detail page shows title, description, price, media (via presigned or public URLs), location.

4
Submit lead

User fills form (name, email, phone, message) and submits. Frontend calls POST /public/listings/{id}/leads with JSON body. Backend validates, loads listing (must be published), creates Lead under org, returns success or validation error.

Flow B: Org — Create listing with photos

1
Create draft

Caller sends POST /orgs/{orgId}/listings with admin key; body includes title, description, price, currency, countryCode, type, status=draft, etc. Backend creates listing with pk=ORG#orgId, sk=LISTING#listingId.

2
Get presigned URL(s)

For each image: POST /orgs/{orgId}/listings/{listingId}/media/presign with { "fileName": "photo.jpg", "contentType": "image/jpeg" }. Backend returns uploadUrl and key.

3
Upload to S3

Client uploads file with PUT uploadUrl (binary body). No auth in the PUT; the presigned URL grants one-time write.

4
Attach keys and publish

Caller sends PUT /orgs/{orgId}/listings/{listingId} with mediaKeys: [key1, key2, ...] and status: "published". Backend writes listing and a copy to public GSI (ENTITY#LISTING#id) so it appears in GET /public/listings.

Flow C: Mark listing as leased or sold

1
Update status

Caller sends PUT /orgs/{orgId}/listings/{listingId} with status: "leased" (for rent) or status: "sold" (for sale). Optional: closedAt: "2025-02-16T12:00:00Z".

2
Backend behavior

Backend saves listing with new status and sets closedAt if not provided. It deletes the item from the public GSI (ENTITY#LISTING#id), so the listing no longer appears in public browse.

11. Key Concepts

Short definitions of terms used in this guide and in the product.

Organization (org)
A tenant in the multi-tenant system: e.g. a brokerage, landlord, or property management company. All listings, leads, and applications are scoped by orgId. No data is shared across orgs.
Listing
A property offered for rent or sale. Has status (draft, published, paused, archived, leased, sold), location, price, media keys, and optional attributes (bedrooms, bathrooms, area). Only published listings appear in public browse.
Lead
An inquiry from a visitor: name, email, phone, message, linked to one listing and one org. Leads are managed in the org’s inbox with status (new, contacted, qualified, closed).
Presigned URL
A time-limited S3 URL that allows the client to upload (PUT) or download (GET) a single object without exposing AWS credentials. DarLink uses presigned PUT for listing media uploads.
Public browse
The experience of listing and viewing published listings without logging in. Implemented by querying the gsi-public-listings GSI; only items with status=published are written to that index.
Admin key
Optional shared secret (ADMIN_API_KEY) used to authorize org-scoped API calls (listings CRUD, media presign). Sent via header x-admin-key or Authorization: Bearer <key>. Phase 2 will add Cognito JWT and RBAC.
Audit log
Append-only record of important actions (e.g. listing created, published, status changed to leased/sold; lead submitted). Stored per org with timestamp; no updates or deletes. Used for compliance and support.

12. FAQs

Frequently asked questions about DarLink’s design, behavior, and usage.

Who can see my listings?
Only listings with status: published appear in public search and on the listing detail page. Draft, paused, archived, leased, and sold listings are not shown to anonymous users. Org members with the admin key (or later, appropriate role) can list and manage all of their org’s listings via the org API.
What happens when I mark a listing as leased or sold?
The listing’s status is updated to leased (for rent) or sold (for sale), and closedAt is set. The listing is removed from the public index, so it no longer appears in GET /public/listings or when opening that listing by ID in public context. The record remains in the org’s data for history and reporting.
Do I need to log in to submit a lead?
No. Lead submission is public: anyone can submit name, email, phone, and message for a published listing. The backend validates the listing exists and is published, then creates a Lead linked to that listing and the listing’s org. No authentication is required for POST /public/listings/{id}/leads.
How do I upload photos for a listing?
Use the presigned upload flow: (1) Call POST /orgs/{orgId}/listings/{listingId}/media/presign with fileName and contentType; (2) Use the returned uploadUrl to PUT the file (binary body); (3) Add the returned key to the listing’s mediaKeys array via PUT /orgs/{orgId}/listings/{listingId}. The S3 bucket is private; the presigned URL grants one-time write access.
Why is there no GraphQL or AppSync?
Phase 1 is REST-only by design. This keeps the stack simple (API Gateway REST + Lambda), avoids GraphQL schema and resolver maintenance, and aligns with the project’s requirement to exclude AppSync and GraphQL. All APIs are documented as REST endpoints.
What is “tenant isolation”?
Every org-scoped record (listings, leads, applications, invites, audit) includes orgId. Queries and APIs always filter by orgId so one organization cannot see or change another’s data. Authorization (admin key or future JWT) must prove the caller is allowed to act for that org.
Which countries/regions are supported?
Phase 1 supports UAE, GCC, and Egypt. Country codes: AE, SA, BH, KW, OM, QA, EG. Listings have countryCode and optional region (UAE, GCC, Egypt). Public listing list can be filtered by country query parameter.
When will login and role-based access be required for org actions?
Phase 1 uses an optional admin key for org listing and media APIs. Phase 2 will add Cognito as the API authorizer and enforce RBAC (e.g. only agents/admins can create listings for their org). The User Pool and app client are already provisioned; integration is planned for Phase 2.
