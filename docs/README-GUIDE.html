1. Application Overview

DarLink is a Bayut-style real estate marketplace targeting Phase 1 MVP for UAE, GCC and Egypt. It supports:

  • Rent/lease and buy/sell listings
  • Multi-tenant SaaS — multiple organizations (brokerages, landlords, property managers) with tenant isolation
  • Public browsing — search, filter, listing details, and lead submission (contact agent CTA)
  • Org-scoped operations — listing CRUD, media upload (presigned S3), admin key–protected endpoints

Phase 1 explicitly excludes tokenization, KYC/AML, and wallets; the stack is REST-only (no AppSync/GraphQL). Compliance posture is informed by VARA-style auditability (immutable audit logs, append-only) without implementing tokenization in MVP.

2. High-Level Architecture

The system is built on AWS with a clear separation: React frontend (Amplify), REST API (API Gateway + Lambda), DynamoDB (single-table), S3 (media), and Cognito (auth).

Environments & IaC

Environments: dev, stage, prod (configurable via CDK context --context env=dev). Infrastructure is defined in AWS CDK (TypeScript) in backend/lib/darlink-stack.ts. Cognito, DynamoDB, S3, API Gateway, and Lambdas are provisioned from a single stack.

GSIs

  • gsi-org-listings — PK = pk, SK = listingStatus (list listings by org with optional status filter).
  • gsi-public-listings — PK = gsi1pk (PUBLIC#LISTINGS), SK = gsi1sk (e.g. published#AE#timestamp) for public browse and filter by country.
  • gsi-org-audit — PK = pk, SK = auditTime for append-only audit log queries by org and time.

Listing status lifecycle (property dynamics)

Listings support a full lifecycle so properties can be marked as leased (rent) or sold (sale) when the deal closes. Only published listings appear in public browse; leased and sold are closed outcomes and are excluded from public search.

draft → published → leased (rent) | sold (sale)

Optional transitions: published → paused (temporarily hide) or archived (remove from marketplace). When setting status to leased or sold, set closedAt to the current ISO timestamp for reporting and audit.

4. Business Requirements

  • Multi-tenant marketplace — Support multiple organizations (brokerages, landlords, property managers) with strict tenant isolation (orgId on every record; no cross-org data access).
  • Rent/lease and buy/sell — Listings support type rent or sale with price, currency, and location attributes for UAE/GCC/Egypt.
  • Lead capture — Public users can submit leads (name, email, phone, message) from a listing page; leads are stored per org and listing for broker/agent follow-up.
  • Listing lifecycle — Listings move through draft → published → (optional) paused/archived. Only published listings appear in public browse; org-scoped CRUD and media upload for authorized callers.
  • Auditability — Critical actions (listing create/update/publish, lead submission, application/contract status changes) must be supportable by an immutable, append-only audit log queryable by org and time (Phase 2 implementation; model and GSI ready).
  • No tokenization in Phase 1 — No wallets, KYC/AML, or token flows; compliance mindset (e.g. VARA-aware) without implementing regulated features in MVP.

5. Functional Requirements

Public (no login)

Browse listings

Search/filter/sort/paginate published listings (e.g. by country, type). Map-ready fields (lat/lng) present; map integration optional.

Listing detail

View single listing with gallery (mediaKeys → presigned or public-read URLs as implemented), description, price, location, and contact CTA.

Lead submission

Submit lead form (name, email, phone, message) for a published listing; stored as Lead linked to listing and org. WhatsApp/callback placeholders acceptable.

Agent/agency pages

Public agent profile and agency pages (placeholders or stubs acceptable in MVP).

Authenticated (role-based)

Listings management

Agents/brokers/landlords/PMs: create, update, delete listings; publish/pause; attach media via presigned upload then add keys to listing.

Leads inbox

View and manage leads by org (and optionally by listing/agent); basic pipeline status (new, contacted, qualified, closed).

Applications & offers/contracts

Lightweight rental application and contract/offer placeholders with real status; full workflows in later phases.

Admin

Org and user management (invites), audit log viewer, moderation flags. Implemented to the extent of admin-protected org listing CRUD and media presign in Phase 1.

AuthN/AuthZ (Phase 1 vs Phase 2)

Phase 1: Cognito User Pool exists; public and admin-key–protected endpoints are implemented. Cognito authorizer on API Gateway and full RBAC/org-scoped auth (e.g. JWT validation in Lambdas) are targeted for Phase 2.

6. Non-Functional Requirements

AvailabilityUse managed AWS services (API Gateway, Lambda, DynamoDB, S3, Amplify) with regional deployment; target high availability; no single-server dependency.
